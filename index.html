PR/PO Extraction Enginein use

A live three-way match. Hundreds of purchase-order PDFs had to become one Excel sheet — 39 columns, one row per line item, header fields repeated down every row — so the detail could be tied back against the client's own records. By hand it was days of typing, and typing is where the errors come from.

The PDFs looked perfectly clean. They were not.

What my eye sawWhat the computer actually readWhy it happens
630498.00000 63049 · 8.000 · 00 The column was too narrow, so the renderer stacked one number over three lines inside a single cell. Your eye joins them back up. The parser sees three fragments.
60 DAYS 6 0 DAYS A kerning gap between the 6 and the 0, read as a space. Same for B Y ROAD and D elivered at Place.
One table, running across two pages 18 columns on page 1, 19 on page 2 A divider line drawn fractionally differently. Hardcode "Rate is column 7" and every rate on page 2 comes out wrong — silently, with no error raised.
The last row of data Total Qty · TOTAL · … The totals row carries numbers and reads like a line item. A naive extractor books a phantom item and the sheet still looks fine.

None of that is visible to a person, because your brain repairs all four while you read, in real time, without telling you it did. The computer has no brain doing that. Every repair has to be written down as code.

What fixed it was giving up on position. Fields get identified by what they contain, not which column they sit in — an 8-digit string is the HSN code, dd-mm-yyyy is the required date, INR is the currency. State codes come from the first two digits of the GSTIN, which cannot lie about itself, instead of the printed State Code label, which the same spacing artefact had corrupted. And a row counts as a line item only if cell 0 is a plain integer and an 8-digit HSN appears somewhere in it — which is what keeps the totals row out.

Two tools, one page: extract_tables() for anything sitting inside the ruled grid, extract_text() plus regex for the free-floating header block. If the data sits inside drawn box lines, it's a table problem. If it doesn't, it's a text problem. Using one tool for both is what makes people give up on PDF extraction.

Then the part that comes from the day job.

Reconciliation checkResult
Sum of extracted line amounts vs the PO's own stated Net AmountTied exactly
Sum of extracted tax vs stated Total TaxTied exactly
Count of extracted line items vs stated Total QtyTied exactly
Net + Tax vs stated Grand TotalTied exactly

This is the same discipline as tying a sample back to the general ledger. If one row had been dropped or one number misread, the sums would not agree. That check is the whole difference between hoping an extraction is right and knowing it is. It also surfaced four real bugs before the output was used — all four in the header block. The line items were correct on the first run; it was the vendor name, the state codes and the payment terms that were quietly wrong.

One edge case I went looking for on purpose: a single-item PO. I built a synthetic one rather than wait to be surprised by a real one. One row out, no phantom totals row. Detection runs per row, so one item and a hundred items take the same path.

What I got wrong, and what I do now.

I uploaded a real purchase order. A live GSTIN, a PAN, both company names, the commercial amounts — all of it, straight up, because I was busy solving the extraction problem and wasn't thinking about the document as client data. Nobody stopped me. Nothing broke. That's the part worth saying out loud.

Afterwards I went and worked out what actually happens, and found I'd been wrong about that too.

What I'd assumedWhat actually happens
An agent running on my own machine keeps the document on my machine It doesn't upload the file — but it sends the extracted text to the API. The model is running on someone else's servers either way
Using a local tool instead of a browser makes client data safe Training and retention policies differ between the two. Whether the data travels does not. If the rule is "no client data to a third-party cloud", both need masking first

Which leads to the thing that resolves it. There's a chicken-and-egg here — to write a masking script you have to understand the document's structure, and to understand the structure you have to look at the document. But you only need to do that once per format, and structure is not data. So now the table structure gets dumped locally with code I already have, the sensitive values are replaced in that text output, and only the masked structure goes anywhere. The model sees the shape of the document and never the client. That step is now built into the ToD file mapper as a first-class part of the pipeline, not an afterthought.

⟶ Runs daily on 3–4 desks. Days of manual entry became one command over a folder.

Honest scope. This is fitted to one PO layout. A new format needs the structure dumped and the content patterns re-fitted — a morning's work, not a rewrite. The five-step method transfers to any document; the parser does not. Client name, GSTINs and figures are withheld here deliberately.

Experiments

Nobody asked for these. They're how I found out what this technology is actually good at — and where it quietly fails.

NotebookLM wired into Claude Code, over MCPin use

MCP — Model Context Protocol — is a standard way to let an AI agent talk to another tool. Here it lets an agent running in my terminal reach into my own Google NotebookLM account.

I have 257 notebooks. NotebookLM's retrieval engine is Gemini's, and it is genuinely good at one job: grounding an answer across fifty or a hundred sources and telling you which source each claim came from. What it will not do is take that answer anywhere. You read it in a browser tab, and then you retype it into whatever you were actually making.

So I split the work. NotebookLM finds and cites. Claude Code takes the raw answer and produces the file I actually wanted. Four tools do the whole thing: notebook_list, notebook_query, chat_configure, refresh_auth.

The first honest limitation I hit: the auth expires, and it expires quietly. The commands now detect it and stop to ask for a re-login, rather than returning a confident answer built on nothing.

Why I reach for a CLI before an MCP serverhow I work

The card above is MCP, so this is the counterargument to my own setup. Most of the time I don't use one.

An MCP server has to describe itself to the model before it can be used. Every tool it offers — the name, the description, the full schema for every parameter — is loaded into the context window and sits there on every single request, whether you call that tool or not. Connect a handful of servers and you have spent tens of thousands of tokens before asking your first question. You pay that rent on every turn of the conversation.

A command-line tool costs nothing until the moment you run it. The agent already knows how to run a shell command; firecrawl scrape "<url>" -o page.md is a dozen tokens, and if it needs the flags it can read --help then, once.

MCP serverCLI tool
Cost before you use it Every tool's schema in context, every request Nothing — a command is a few tokens
Where the output lands Straight into the context window, all of it In a file. You choose what to read into context
After the session ends Gone with the conversation A command you can rerun, schedule, or pipe into the next one

That middle row is the one that bites hardest in practice. Scrape a long page through a tool that returns its result directly and you have just spent fifty thousand tokens of context on something you wanted four paragraphs of. Write it to a file and you read the four paragraphs.

Where MCP genuinely wins, and why I still use it.

When the thing has no command line and lives behind a login it holds itself — NotebookLM is exactly that. There is no notebooklm binary; the session state, the auth, the query interface only exist through the server. Paying the context rent is worth it because the alternative is not a cheaper tool, it is no tool.

So: CLI by default, MCP when there's no other door in.

Getting data off the web — an escalation ladderin use

Four different tools, and the whole skill is knowing which rung you're on. Every one of these is heavier, slower and more expensive than the one above it, so you start at the top and only drop when the page refuses.

The situationWhat I reach forWhy that one
I have the URL. Static page, or a JavaScript app Firecrawl scrape One command, clean markdown out, no browser to babysit. Handles SPAs, which is where naive scraping usually dies
I don't have the URL, or I need every page under a section Firecrawl search / map / crawl Find or enumerate first, then scrape. Bulk-download a docs site to local files and read it offline
The platform fights back — LinkedIn at volume, YouTube comment threads Apify actor Someone has already solved the proxies, the rate limits and the layout changes, and is maintaining it. Pay per event. Writing this yourself is a hobby, not a task
It needs clicking — forms, pagination, a login, a multi-step flow Playwright CLI A real browser I drive myself, scripted, repeatable, headless when I want it
It has to be my browser, already signed in Claude in Chrome Runs in my live session, so the logins are already where they need to be. Last resort — a human in the loop, and slow

The two things that took actual use to learn.

Scrape to a file, then read the file. Most of these tools will happily answer a question about a page for you, and that convenience costs extra credits and dumps the whole page into context. Saving it and searching it myself is cheaper and I can go back to it tomorrow.

And every one of these bills differently — per event, per credit, per page. Reaching for the heavy tool first is how a scrape that should cost pennies quietly doesn't.

Studying a writer's craft — /anulata, /kanchan, /craft-newin use

This is the one I do for love, and it holds the best engineering on this page.

I take Hindi audio stories off YouTube and push them into notebooks — Anulata Raj Nair, 113 sources; Kanchan Pant, 61 — then study how the writing actually works. Nine lenses per story: how it opens, the relationship architecture and who holds power at each stage, what texture carries the feeling, what is withheld, how the dilemma is loaded on both sides so that neither choice is free, the subtext, where the perspective turns, how it lands, and the narrator's voice.

Five modes: a cross-story signature, one story dissected, a single lens run across the whole corpus, a critique of a draft I've written myself, or seeds for new premises built out of her structures.

The architecture is the part I'd defend in a review.

Every piece of analysis logic lives in one shared file. A writer's command is a nine-line stub pointing at it. /craft-new "<name>" builds a new one — it finds their notebook, refuses to guess the two things it must never guess (pronouns, and whether quotes should come back in roman script), writes the stub, and offers to index the corpus. Edit the shared file once and every writer command changes at the same moment.

And the part that took a wrong answer to learn.

One notebook holds fifteen sources uploaded by mistake — a scooter review, a politics clip, some music. The notebook's own auto-summary confidently credited the writer with "sociopolitical critique" that had come from the politics clip. Nothing about the answer looked wrong. So the command now carries a permanent ignore list, and when an answer cites anything on it, that answer is thrown away and the query re-run naming the story explicitly.

Evidence rule throughout: verbatim quotes only, roman-script Hinglish with the English meaning on the next line, and anything I'm not certain is verbatim gets labelled as not verbatim.

Marking scripts with open-weight models — Ollama + Doclingin progress

Evaluating answer scripts, where two problems sit on top of each other.

The first is the scans. Scanning is cheap now, so people send whatever the phone produced — skewed, grey, compressed, handwriting running across the ruling. That is not a document, it is a photograph of one. Docling is the part that turns it back into structure worth reading; a plain text dump off a scan like that is close to useless.

The second problem is the one that actually decides whether this can work.

The marking scheme is the expensive constant. Every script gets judged against the same scheme, so the naive build re-reads that scheme for every single paper — the same tokens, the same reasoning, the same cost, over and over, for the one part of the job that never changes.

So it gets read once. The scheme is parsed into a structured artefact up front — question by question, marks, what earns each one — and the project laid out so every paper after that is a cheap comparison against something already understood, instead of a fresh act of comprehension. The variable input stays variable. The constant stops being paid for repeatedly.

Running it on Ollama, with open-weight models on my own machine, is the other half. Student answer scripts are somebody else's work and somebody else's name. That is the same reason my statutory RAG pipeline is moving local: some material should not leave the machine at all, and the only honest way to guarantee that is for the model to be sitting on it.

Honest status. In progress, not deployed. The open question is quality: whether a model small enough to run locally can hold a marking standard steady across a stack of papers, which is exactly what a human examiner struggles with too. I'd rather find that out than assume it.

Reading the market before preparing for itbuilt

Before writing a single line of interview preparation, I went and found out what was actually being asked.

Three staged runs through Apify's LinkedIn actor — 303 posts, then a pass for the comment threads, then 800 posts across eight question-focused queries — plus two published question banks pulled with Firecrawl. Then the filter: what people report actually being asked, against what the syllabus says will be.

⟶ The finding changed the plan. Demand sat in controllership, not where I had assumed.

Every claim in the output traces back to the post it came from, in a written source file. If a conclusion can't be traced, it isn't a conclusion.

What went wrong, since that's the useful half: the comment pass under-delivered badly — 307 posts but only 187 comments — so a chunk of what I wanted was never there. The scrape reported success. Checking the counts is what caught it.

Exam prep as a retrieval problemongoing

Official ICAI material in one notebook. What students said about the paper they had just walked out of in another. The first tells you what is examinable. The second tells you what is actually being asked this cycle — and those are not the same list.

Put both in front of the same retrieval engine and the high-value topics separate out on their own. Then generate questions and answers against that shortlist rather than against the whole syllabus.

Two sources, two different jobs: the official one for authority, the crowd one for currency. Neither is any use alone.
